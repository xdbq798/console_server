## Apipost 登录 403 排查

- 报错 `{"detail":"缺少会话操作保护请求头"}` 来自 `src/console_server/api/auth.py:132-152` 的 `validate_cookie_request()`。
- 会话类接口（login / logout / logout-all / refresh）要求：`Content-Type: application/json`、请求头 `x-csrf-protection: 1`，且 Origin/Referer 若存在必须在 `AUTH_ALLOWED_ORIGINS` 内（默认只允许请求 base_url）。
- 已在 `docs/openapi.json` 为上述 4 个接口补充 `x-csrf-protection` header 参数，重新导入即可带出；已导入的项目可在 Headers 中手动加该头。
- Apipost Web 版若带 `Origin: https://workspace.apipost.net` 可能触发来源校验 403，可改用桌面客户端，或在 `.env.dev` 配置 `AUTH_ALLOWED_ORIGINS=["https://workspace.apipost.net"]` 后重启服务。

## 日志系统接入 loguru（方案 B）

- 依赖：`uv add loguru`，同时 `uv remove colorama`（原彩色 print 体系退役）
- 新增 `core/logger.py`：InterceptHandler 把标准库 logging 全量转发给 loguru（uvicorn/apscheduler/sqlalchemy 一并收编）；setup_logging() 读 `GLOBAL_LOG_LEVEL` / `LOG_FORMAT`（json=结构化），NO_COLOR 或 RUNNING_IN_DOCKER 时关彩色
- 保留 env.py 的 `SRC_LOG_LEVELS` 机制：loguru 用 `logger.bind(log_source=...)` + sink filter 实现，`module_logger(source)` 是新入口；模块日志等级从对应 `XXX_LOG_LEVEL` 环境变量读
- 坑 1：InterceptHandler 帧回溯深度必须数完调用链上所有 `logging.__file__` 帧（depth = 1 + 计数），否则显示 `logging:callHandlers` 而非真实调用方
- 坑 2：Starlette 后注册的中间件先执行；RequestLoggingMiddleware 要在 AuthMiddleware 之后 add_middleware 才能记到 401 等被认证层拦截的请求
- 新增 `middleware/request_logging.py`：每请求一行日志（方法 路径 -> 状态 耗时ms），响应头带 `X-Request-ID`（uuid 前 8 位），5xx 记 WARNING
- `utils/console.py` 的 print_* 保留为 loguru 适配层（`logger.opt(depth=1)` 保证定位到真实调用方），db/database.py、api/auth.py 调用方零改动
- main.py：setup_logging() 必须在所有本地/第三方模块导入前调用；print_* 换 log.success/warning/info；`log.error(..., exc_info=True)` 换 `log.exception(...)`
- 已验证：启动横幅、uvicorn access log、apscheduler 日志全部统一 loguru 格式；请求日志带耗时和 request_id；`GLOBAL_LOG_LEVEL=WARNING` 过滤与 `LOG_FORMAT=json` 输出均正常
- README 与 docs/后端启动教程.md 环境变量表补充 LOG_FORMAT / NO_COLOR
